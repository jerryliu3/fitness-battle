# Daily competition waves

New sport registrations, including onboarding, join the next 06:00 America/New_York benchmark. Before 06:00, that means today; after 06:00, tomorrow. Sunday after 06:00 joins Monday's new week. Bounds are half-open: `[start, next Monday midnight)`. Display the finish as Sunday 11:59 PM Eastern. Renewals start Monday 06:00, leaving a six-hour queue after the old week ends. Training charts and streaks still use calendar Monday–Monday weeks.

## Registration and assignment

The existing `wave_enrollments` table is the queue. Start/end timestamps derive its queued/running state; there is no second status clock. A unique user/sport index allows one current registration per sport. `registered_at` records server acceptance and `field_id` references the canonical field after assignment. A trigger verifies the referenced field's sport, bounds, Crew context and membership. Peer/generated arrays on an enrollment are compatibility caches; they do not authorize seating.

The versioned account save remains the single public registration write. It serializes with finalization using account and sport/start advisory locks, preserves server metadata, rejects backdated joins, and allows cancellation only before the start. Client requests crossing the cutoff are rebased by the API and returned to the client. A database boundary race returns a retryable registration error. Started enrollments can stop renewal, but cannot leave or change Crew context mid-wave. Implicit Monday renewals are protected even when the account has not yet loaded its new enrollment.

`resolve_week_field` finalizes every eligible registration for a sport/start together on the first authorized read at or after the benchmark. The official start and eligible activity window remain 06:00 regardless of when that read happens. This requires no cron or new scheduler. It includes automatic Monday renewals from accounts that have not reopened the app, and excludes opt-outs. All readers reuse that frozen assignment.

Only registrations with the same sport, benchmark and finish share a field. Solo matching uses entry rating for the product's track (GPS for running/cycling, Open for walking/strength), prioritizes mutual repeat choices and nearby ratings, and limits the rating spread to 400. A group contains up to eight athletes; remaining seats use stable generated rival IDs stored by the database. Crews seat only their actually registered members in that wave, with generated fillers for empty seats. Roster choices do not change after start. Leaving or deleting a Crew preserves started competition membership/history.

Before the start, clients show you and seven mystery competitors, exact start/end labels and Cancel registration. No field names, opponent IDs, ranks or competition milestones are revealed/earned while queued. At start the app refreshes the canonical roster; a failed read keeps a waiting state. Generated competitors are disclosed after reveal. Every athlete's scoring uses the same persisted field bounds. Short midweek/Sunday waves currently use the existing rating adjustment rules; no duration-based rating scaling is introduced. A workout is included by its start timestamp; sessions crossing a boundary are not split.

## Settlement and compatibility

The deadline is hard: only facts accepted by the database before the exclusive close count. A backdated workout received after close remains in training history and cannot change competition distance, milestones, placement or rating. Later edits, exclusions, deletions and resyncs also cannot change the accepted facts of a closed round. There is no sync grace period.

`private.competition_fact_versions` records immutable activity and sleep input revisions with a database acceptance time. Deadline readers select the last accepted version before close. Shared advisory locks let an in-flight accepted write finish before a closing read; this freezes scores even when the first reader arrives hours later and requires no deadline cron. Field entry ratings are snapshotted so another athlete's settlement cannot change the opponent ratings used for a closed result. Migration backfills the currently stored activity facts and preserves existing archived results; it cannot reconstruct pre-migration edit history.

The authenticated application server derives ratings, entry locks, milestone receipts, freeze budgets and results from stored state and accepted inputs. The account document supplies user intentions, never authoritative score values. New manual rows remain Open-only; existing tracker metrics cannot be changed through an account document. Direct authenticated score/input-table writes and the old client score RPC are revoked. The server-only commit RPC rechecks the account revision, accepted-input receipt revision and deadline crossing before committing. Client scoring remains an optimistic presentation of the same shared rules.

Account GET resolves each closing field before scoring it. Account PUT recomputes a device-submitted rollover against the stored registration and fresh field totals, so a stale closing snapshot cannot become the final place. Failed field reads return 503 and do not persist estimated results. Configured clients also defer local settlement for unresolved fields. Existing started windows and archived results are retained; legacy registrations that were never assigned a field receive a separate frozen field without changing anyone else’s roster; the new schedule applies to new registration and renewal. The older seating RPC delegates to resolution and cannot create an unregistered or late seat.

The shared density matcher accepts an explicit derived window, including `instantWaveWindowAt(now)`, using the same enrollment shape. Public registration uses daily waves. No instant-only schema is introduced.

Sleep/Recovery follows the same queue and renewal schedule through its existing health rating model. Its ranking remains the existing generated sleep contest, rather than the sport multiplayer matcher. Sleep readings have wake-day granularity; deciding whether the start day's preceding night should count is a separate scoring decision.

## Deployment and verification

Apply `20261028210909_daily_competition_waves.sql`, `20261028231429_daily_wave_review_fixes.sql` and `20261029001132_competition_score_authority.sql` in order with the server and clients. The web/API environment now requires server-only `SUPABASE_SERVICE_ROLE_KEY` for ordinary score commits; it must never enter the client bundle. Older clients cannot bypass queue or cancellation restrictions; their immediate-registration UI should be upgraded with the server. No production deployment is performed by this change. See the [local verification](reviews/daily-waves/local-verification.md) and [code review](reviews/daily-waves/code-review.md).

Coverage includes timezone cutoffs, spring/fall DST, Sunday rollover, queued scoring/identity suppression, cancellation, renewal, canonical roster failures, shared field identity, rating matching, generated fillers, stale renewal cancellation, Crew departure/deletion, and public/private database privileges. SQL fixtures run in a rollback transaction against the migrated schema. Existing TypeScript scoring, replay, provider lifecycle and interface tests exercise active fixtures registered before their benchmark.
